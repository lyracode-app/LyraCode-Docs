# 第 10 章：子代理编排——让主模型把独立子任务分出去

## 10.1 子代理是什么

主模型负责理解你的总目标、拆分任务和汇总答案；子代理是预先配置的其他模型，收到一个边界清楚的小任务后独立分析，只把最终结果返回给主模型。

它适合“可以同时做”的事情，不适合必须一步接一步完成的流程。

| 适合 | 不适合 |
| --- | --- |
| 分别审查三个互不相关的文件 | 先改数据库再根据结果改接口 |
| 同时调研多个方案 | 只读一个已知文件 |
| 一边查资料一边做独立风险审查 | 一个只有两步的简单任务 |
| 多个模型各给一套方案 | 多代理同时修改同一个文件 |

## 10.2 配置前准备

至少先在 **设置 → 模型服务** 保存一个可用服务商和模型。子代理可以使用与主模型相同或不同的模型，但都要消耗对应服务商额度。

## 10.3 新增子代理

1. 打开 **设置 → 子代理编排**。
2. 点击新增。
3. 从已有模型服务中选择服务商和模型。
4. 输入一个清楚的名称，例如“代码审查员”。
5. 在说明中写它擅长的任务和边界。
6. 启用并保存。

说明示例：

```text
擅长 Kotlin/Compose 代码审查。重点检查崩溃、状态同步、权限和并发问题。
只报告有证据的问题，给出文件与位置；不负责直接改文件。
```

“万能助手”这种说明没有路由价值。一个子代理最好只有一类明确专长。

## 10.4 启用子代理能力

配置完成后，回到对话动作面板确认子代理功能已启用。只有启用的配置才会提供给主模型。子代理对话不会混入普通历史列表，主会话主要收到最终结果。

## 10.5 怎样提出适合并行的任务

可以直接说：

> 请把任务拆成三个独立审查：安全、性能、用户文档。适合时调用已启用的子代理，最后去重并按严重程度汇总。先不要修改文件。

你也可以只说明总目标，由主模型判断是否需要分派。子代理不是越多越好：任务太小会增加 Token、等待时间和结果冲突。

## 10.6 结果怎样复核

主模型应：

1. 标明哪些结论来自子代理；
2. 去掉重复意见；
3. 对互相矛盾的结论回到源码或数据核查；
4. 不把未经验证的猜测直接当事实；
5. 在需要修改共享文件时统一安排，避免冲突。

用户也应要求证据，例如文件路径、日志、官方文档或可复现步骤。

## 10.7 成本与速度

并行可以缩短墙钟时间，但不会减少总调用量。三个子代理通常意味着额外三次模型上下文和输出费用。可以给简单审查配置轻量模型，把昂贵模型留给主模型汇总。

## 10.8 常见问题

### 主模型没有调用子代理

确认配置已启用、对话动作面板已打开该能力，并且任务确实能拆成独立部分。简单任务不调用是正常行为。

### 子代理结论互相冲突

让主模型列出分歧点，并回到原始文件或权威来源逐项验证，不要按“多数票”决定技术事实。

### 任务变慢或费用升高

减少子代理数量，缩短每个说明，限定输出格式，并只在复杂任务使用。

### 能否让多个子代理一起改同一文件

不建议。并发写同一路径容易冲突。让子代理只分析，由主模型或一个明确的执行者统一修改。
